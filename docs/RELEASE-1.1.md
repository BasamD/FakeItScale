# ScaleSim 1.1 — dial, clear status, and reliable reconnects

## Try first

1. Extract this version to its own folder and launch ScaleSim.exe. Keep your saved 1.0.1 ZIP as a fallback.
2. In 1 Connection, start the TCP listener and connect WasteWORKS as before.
3. Choose Manual and drag the dial. The next scheduled frame uses the new weight. Use exact entry for any integer value; the dial and nudge buttons make 20 lb steps.
4. Try Automatic. Watch the stable-send progress and last transmitted weight. Default behavior is still ten identical frames before a 20 lb decrease.
5. Pause and Resume. Try Apply on the interval while a hold is in progress; it preserves your place.
6. Turn on Show transmission log or Reduce motion as desired.

## New interface

- Grouped connection, weight, and streaming sections; inactive mode/transport fields are hidden.
- A draggable, keyboard-accessible manual weight dial, exact entry, presets, and ±20 lb buttons.
- A dashboard with frame count, last transmitted weight/time, errors, connection state, and automatic stable-send progress.
- A simple truck-on-scale illustration driven by actual completed writes, with Reduce motion. It cannot confirm a WasteWORKS capture.
- Optional bounded log and inline validation instead of extra error popups for invalid weights/settings.
- Preview.png is a real screenshot generated by the Windows build, not a proposed design.

## Reliability review and fixes

- Invalid Manual/Automatic drafts no longer leave the selector disagreeing with the running engine.
- Applying only an interval change preserves the automatic weight, hold count, and paused state.
- TCP disconnect detection runs independently of the send interval and works while paused; unexpected inbound bytes cannot mask a disconnect.
- Pending UI events are bounded, so fast streams or a temporarily busy UI cannot accumulate an unbounded callback queue.
- Saving preferences retains valid applied values instead of invalid draft weight settings.
- Automatic configuration and mode changes are applied together under the engine lock.

## Validation and limits

Sixteen automated core/TCP checks cover exact frames, ten-send holds, manual changes, pause/resume, min/reset cycles, failed-write counting, reconnects, long intervals, bounded logging, and listener cleanup. The Windows pipeline additionally checks the visible UI, dial/preset changes, invalid-mode recovery, live TCP output after a dial change, connection controls, and clean shutdown before packaging.

The byte protocol is unchanged. Virtual serial pairs still require a separately installed signed Windows driver. Real COM-driver and WasteWORKS tests require your Windows setup. A completed local write does not prove the receiver captured it. The app remains unsigned, portable, and self-contained.
